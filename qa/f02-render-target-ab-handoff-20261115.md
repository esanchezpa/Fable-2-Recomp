# F-02 render-target optimization: bounded A/B handoff

## Decision

Select F-02 (`faster_render_targets`) as the next isolated performance validation. Do not port another implementation: the candidate is already present in the pinned ReXGlue SDK (`d6a2acfc`) and is enabled in the project config. No code change is justified until a controlled run shows that the existing optimization regresses or fails to activate. The prior `33 → ~57` claim at 2x is historical author evidence only; this handoff does not adopt it as a current benchmark result.

## Exact implementation and dependencies

- `thirdparty/rexglue-sdk/src/graphics/d3d12/command_processor.cpp`: `IsDepthClearRectangle` is checked in the D3D12 draw path. When `skip_depth_clear_transfers` and `execute_unclipped_draw_vs_on_cpu` are both enabled and the predicate matches, it removes the depth-transfer list before the render-target cache processes transfers/resolve clears.
- `config/fable2_config.toml` and the matching embedded template in `src/core/fable2_config.cpp`: `[patches] faster_render_targets = true` seeds both SDK cvars. Setting it false is the single A/B toggle; it restores the SDK defaults for this feature pair.
- Dependencies: Windows D3D12 path and the matching F-02 SDK code already in the pinned submodule; no new library or package. Do not test this as a Vulkan optimization.

## Spain compatibility risk

The predicate is language-independent, but its safety depends on actual draw state and the bounds inferred by `DrawExtentEstimator`, not on language. Spanish GOTY runtime compatibility has not been empirically validated for this optimization. In particular, the audit notes that the rectangle predicate checks `min_y` but not `max_y`; this is not proof of a defect, but any depth corruption, missing geometry, purple band, or visual mismatch in the ON variant is an immediate rollback. Verify the QA clone's XEX identity before the pair and leave original game files untouched.

## Why this candidate, not the other audited work

- F-03's CPU terrain/skinning evaluators are already in the pin and enabled by default; their shader-hash dispatch and Spanish GOTY activation are not confirmed, so a source port would duplicate existing code.
- F-04 adds `WakeByAddressAll`, but the audited runtime has no matching `WaitOnAddress` waiter; alone it does not remove a production spin/wait.
- F-05a/b are not in the pin, introduce cross-thread D3D12 command recording with documented `DEVICE_HUNG` lifecycle hazards, and the reported warm-cache FPS comparison was neutral. They need broader lifecycle testing before any port.
- F-06 needs the external prebuild list staged beside the executable and a Spain-data/hash parity gate; it has no local cold-start benchmark. It is not the lowest-risk next step.
- The existing `docs/FPS_CAP_INVESTIGATION.md` says `Yield_82CBD098`'s ~150M calls had negligible duration and did not limit the main-loop cadence. That conflicts with the ~13.7% CPU attribution in `docs/hotfunc_overrides.md`; therefore yield batching is not selected without resolving the difference in profiler context.

## Real toggle and valid variant scope

- The real project option is `[patches] faster_render_targets` in `fable2_config.toml`, parsed by `src/core/fable2_config.cpp` (built-in default `true`). `Fable2App` applies it in `src/core/fable_2_app.h`: only while each SDK flag is still at its default source, it seeds both `execute_unclipped_draw_vs_on_cpu` and `skip_depth_clear_transfers` to the same value. This is the supported single user-facing toggle; do not invent a CLI flag or change just one SDK cvar.
- In the pinned SDK, `skip_depth_clear_transfers` itself defaults `true`, is hot-reloadable, and is documented as dependent on `execute_unclipped_draw_vs_on_cpu`, which also defaults `true`. In `IssueDraw`, `SetDepthOverwrittenByNextUpdate` receives true only when both flags are true and `IsDepthClearRectangle` matches. The predicate requires an unclipped rectangle-list auto-index draw with 3 indices, a depth+stencil unconditional write/replace, full stencil write mask, valid vertex data, and a nearly full-pitch horizontal extent. It checks `min_y` but not `max_y`; this is a correctness risk to watch visually, not a proven bug.
- Therefore the valid source-level variants are exactly A: `faster_render_targets=false` (both flags seeded false; predicate path disabled) and B: `true` (both seeded true; eligible draws may skip depth transfers). Keep EXE, runtime DLL, GPU DLL, XEX, data, resolution and all other configuration byte-identical. The current QA `fable2_config.toml` does **not** contain this key, so merely using it as-is does not create an OFF variant: the loader falls back to the built-in `true`. Add the one key to the disposable QA config only after making a verified byte-for-byte backup; verify the loaded build and seeded cvars from logs/source or an explicit config diagnostic before counting measurements. Do not rely on the generic `loaded config` line alone, which does not report the effective value.
- A historical visual route exists: `city-S3-route-pair-20261113.json` records camera/movement rehearsal in `Hero 1 / Ciudad Vieja de Bowerstone` with matching route durations about 4.81/4.82 s and matching save hashes. It was explicitly **not** a performance benchmark and used two QA clones whose EXE/DLL hashes now differ (`gameplay-pair`: `25AFC…`/`C242…`/`90ABD…`; `gameplay-qa`: `7A499…`/`3621…`/`3475…`). It demonstrates a possible visual route only; it is not a comparable F-02 A/B pair. Existing clones are thus not currently a valid binary-matched variant pair. Reuse the route only as a navigation rehearsal, then run A/B sequentially on one verified build/config tree or make matched copies from a single manifest after backup/preflight.

## Metric and cost

- Primary feasible metric for an initial bounded validation is external per-process GPU Engine utilization plus process CPU time over identical fixed-duration route windows, sampled outside the game; these quantify host resource cost, not FPS. Record wall-clock/QPC boundaries and discard menu/load/observation intervals. Compare paired medians and run-to-run spread; require visual parity. The Windows GPU Engine counter was present, but its correlation to guest draw work is coarse and counters must be validated for this PID/device.
- PresentMon/CapFrameX can add host present timing/metadata only if a valid CSV is produced and ETW loss counts are acceptable. `PresentId`, DXGI Present calls, `xe_swap`, guest-output refreshes, or frames produced are not by themselves proof of unique guest images displayed. Prior traces explicitly lack validated guest-content-to-display correlation. Do not report these as guest FPS.
- Do not enable Tracy/Optick, RenderDoc, PIX, or the in-game Lua sampler for this comparison: Tracy/Optick require instrumentation/handshake and add measurement cost; RenderDoc changes marker/capture behavior and previously correlated with startup crashes; PIX lacks `pixtool.exe`; the sampler's runtime path remains unvalidated. Use a separate instrumented diagnostic only if external metrics show a concrete question worth its overhead.
