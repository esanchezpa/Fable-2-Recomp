## 14. Auditoría de relojes y diagnóstico ETW

- `CommandProcessor::ExecutePacketType3_XE_SWAP` registra el intervalo en `GuestFrameMeter` **después** del limitador de frame y **antes** de `IssueSwap`; el contador F3 expresa la media de intervalos de paquetes XE_SWAP de una ventana de medio segundo, no la distribución por frame ni imágenes únicas mostradas. El test nativo `tests/native/test_guest_frame_meter.cpp`, compilado y ejecutado en QA, pasó para 30, 60, 120, 144, 165 y 240 Hz sintéticos, incluye un stall y mantiene instancias independientes. Esto prueba el cálculo sintético, no su relación con la pantalla.
- `Presenter::RefreshGuestOutput` incrementa `guest_frame_count_` tras refrescar con éxito una salida guest activa. La salida preparada puede reemplazar otra pendiente antes del consumo (`presenter.cpp:565-605`), por lo que este contador tampoco demuestra que cada imagen se haya mostrado ni que su contenido sea diferente.

## 43. Plan de pruebas F-04 y regresión reproducible del inspector de atlas

### F-04: protocolo y matriz de pruebas antes de cualquier port

- **Comparación de implementación:** en el pin del SDK (`d6a2acfc`) `ExecutePacketType3_EVENT_WRITE_SHD` hace `memory::store` al host pointer traducido del guest address. La ruta `WAIT_REG_MEM` actual lee el valor repetidamente; para esperas largas llama `PrepareForWait`, duerme si `vsync` está activo o `MaybeYield` si está apagado, sincroniza memoria y luego vuelve a evaluar el predicado. `PrepareForWait`/`ReturnFromWait` son no-ops en el command processor base. La búsqueda en `src/` e `include/` del pin y de la rama fuente candidata no encontró ninguna llamada a `WaitOnAddress`; el commit F-04 solo añade `WakeByAddressAll` después del store. Por tanto, F-04 aislado no cambia el waiter actual y no hay una ruta de producción a la que pueda conectarse una prueba de integración todavía.
- **No copiar la primitiva del candidato como test:** un test que llame Win32 `WaitOnAddress` + `WakeByAddressAll` directamente solo probaría el contrato del sistema operativo, no el runtime ReXGlue. Tampoco se debe sustituir `memory::store` por un store atómico sin demostrar que el backing guest address tiene alineación, estabilidad y acceso compatibles, ni asumir que todos los writes/esperas pertenecen al mismo proceso/host address. No se modifica código ni pin.
- **Pruebas de unidad requeridas cuando exista una pareja producer/waiter en fuente:** (1) value ya cambiado antes de entrar al wait: retornar tras reevaluar sin depender de wake; (2) waiter estacionado antes del store: el store seguido de wake permite progreso; (3) wake espurio sin cambio de value: permanece bloqueado/reintenta sin declarar la condición satisfecha; (4) varios waiters sobre una misma dirección: todos despiertan y cada uno vuelve a evaluar su propio predicado; (5) cancelación/shutdown durante espera: salida acotada y sin uso del address después de liberar/desmapear guest memory; (6) counter wrap/endian conversion: el valor observado respeta `GpuSwap` y la condición guest. Usar `std::atomic::wait/notify` como modelo determinista en test portable si el production adapter se diseña así; en Windows, el test de integración debe invocar el adapter de producción y las APIs Win32 reales, no un fake de wake.
- **Prueba concurrente para cerrar lost-wakeup:** cada iteración inicia con dirección alineada y valor `n`; sincroniza con barreras para ejecutar ambas ordenaciones —(a) producer almacena `n+1` antes del wait y (b) waiter observa `n` y se estaciona antes del store—; acota el tiempo por iteración y verifica valor `n+1`, wake count y terminación. Añadir iteraciones con N waiters y shutdown/rebind de memoria. Event writes conservan el orden `convertir endian → store → wake`; el predicate loop no puede depender de que wake signifique que el valor esperado se alcanzó. Cualquier timeout es fallo del test, no “frame pacing lento”.
- **Gate separado de rendimiento/compatibilidad:** después de unit tests y build Windows D3D12 pareado, comprobar durante una sesión instrumentada que el address escrito por `EVENT_WRITE_SHD` coincide con el address realmente esperado por el waiter en Fable II; medir CPU idle, cadence guest y timeout/spurious wakes frente al baseline con misma escena/caché. Repetir cold/warm, shutdown y prueba XEX Spain con hash gate. Sin esos pasos, el cambio no puede promoverse a portado/medido.
